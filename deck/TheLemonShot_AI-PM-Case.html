Task 1 · Why these three

One loop, three flywheels

Data flywheel

Every campaign writes outcomes, including sales, back to one creator graph. Better matches lead to better results, more campaigns and more data.

Adoption flywheel

Proposal Copilot builds the habit in Slack, Sheets and Slides. Match and Pulse ship into the same surface, so there is almost no new workflow to learn.

Capability flywheel

Each build reuses the data mart, prompt library, error-handling templates, evals and governance, so it ships faster than the last.

Why it fits a service agency

It covers win rate (Proposal), results and retention (Match) and margin per head (all three). Time saved becomes capacity for more pitches, not smaller invoices.

The combination matters more than any single tool. Every shortlist and every campaign writes to one creator performance graph. Adoption compounds too, because each tool lands in the same Slack and Sheets surface. And for a service business: more wins, better results, more output per head. One caveat: if clients pay by the hour, efficiency can cut revenue, so this pushes us toward retainer or value pricing.

Why these models

Thai-language quality, proven on our eval set, not assumed. Reliable JSON via structured outputs. No open-source models in v1: self-hosting them needs engineers we don't have.

Why n8n

Self-hosted, so data stays under our control (PDPA). Code nodes and Slack approvals built in. Make bills per module run, so a loop over 60 creators multiplies cost. LangChain needs engineers.

Design rule

The model is a config value. The data model is the asset. Prompts and schemas are versioned, and vendors can change without a rebuild.

Five layers, left to right. Public metrics need no consent; audience demographics need the creator's own OAuth grant, which is why Creator House onboarding is on the critical path. BigQuery is the only place scoring reads from, so API changes never break scoring. Models are swappable; our data model is the asset. If asked about alternatives: Make would work and the logic carries over, but it bills per module run. LangChain is a code framework, so it needs engineers we don't have. Open-source models become an option in Year 2 if cost or data residency calls for them.
Task 2 · The exact logic in n8n

CM-01: brief to shortlist in about 20 nodes

1 · Intake

Form Trigger, or a PDF via Extract From File. Then HTTP POST api.anthropic.com/v1/messages with claude-sonnet-5-5 and output_config.format set to a JSON schema. Code validates the result; gaps go back to the requester through Slack Send and Wait. On error, the fallback is OpenAI /v1/responses.

2 · Retrieve and score

BigQuery GoogleSQL applies the hard rules: platform, consent, not blocked, no competitor work in 90 days. Code scores performance (Bayesian-shrunk history plus engagement vs tier), audience fit and cost per engagement. CM-02 refreshes stale profiles.

3 · Judge

One Claude call per creator, in batches of 5, 1 s apart. It returns brand fit 0-100, a rationale citing posts, risk flags and confidence. A failed call becomes "not assessed" and never blocks the shortlist.

4 · Deliver and learn

Weights by objective, budget fit, at least one rising creator, flags shown and never dropped. Then Drive copy and Sheets, then Slack Send and Wait (approval, restricted approvers), then Proposal Copilot. Every decision is logged to BigQuery.

This is the exact flow I'd configure, and the importable workflow exists with demo data. Hard rules run in SQL before any AI. The LLM does two narrow jobs: parse the brief and judge brand fit, both with a JSON schema so the output is machine-checkable. Everything that leaves the system goes through a human approval in Slack.

Task 3 · Risks I must control

Three risks to control before any third-party gen AI touches client work

01

Creator likeness and personality rights

Risk

A vendor tool reproduces a creator's face, voice or style beyond what they agreed to, or trains on creator assets. Our celebrity network raises the stakes.

Controls
  • AI Likeness Rider: opt-in per use, payment for synthetic variants, approval rights, a kill switch, no vendor training.
  • Consent registry checked in code before any generative step that touches creator assets.
  • Platform labels: TikTok, YouTube and Meta AI-disclosure rules.
02

Synthetic media licensing and output IP

Risk

Clients receive AI-generated assets whose ownership is unclear, or that infringe third-party IP through the vendor's training data.

Controls
  • Vendor contract: output ownership to us or the client, IP indemnity, a warranty that training data is licensed.
  • Asset register: model, prompt, human edits and approvals, plus C2PA credentials where supported.
  • Client contracts disclose AI use and allocate risk.
03

Training-data privacy and client confidentiality

Risk

A vendor retains or trains on briefs, personal data or results. With 750+ brands, data could leak between competing clients through shared retrieval.

Controls
  • Contract terms: no training, limited retention, a DPA, PDPA cross-border safeguards.
  • Minimize: send aggregates, redact personal data, and isolate each client in retrieval.
  • Operate: role-based access, audit logs, a DPIA before go-live.
Principle: consent and confidentiality are enforced in code, not in a policy document. If the registry says no, the workflow cannot run.
These must be in place before any third-party generative platform enters client work, which is also why DCO waits. The most agency-specific risk is number three: we serve competing brands, so a shared AI memory could leak one client's strategy into another's proposal. Retrieval is isolated per client, by design.

Task 4 · Human-in-the-loop design

Empowerment by design: guardrails, overrides, feedback

GProduct guardrails

  • Evidence or silence. Every score shows its breakdown, sources and data date. Thin data gets "low confidence", never a guess.
  • Hard rules run before the AI. Exclusions, consent, blocked creators and budget caps are code the LLM cannot override.
  • No autonomous outward actions. Clients, creators and spend each need a named approval, with an audit trail.
  • Spend caps in Pulse: at most ±20% a day, a 24 h cooldown, one-click revert.
  • AI-DRAFT watermark until a human marks each section reviewed.

OCreative override controls

  • Swap, remove, add or reorder any creator. Edit anything. Regenerate a section with an instruction.
  • Human-owned zones: the Big Idea and creative territories belong to the strategist. AI offers options only on request.
  • Tune the matrix per brief with presets like "proven sales" or "rising creators".
  • One-click override reasons. Never penalized. The human choice is the decision of record.
  • An off switch per brief for any squad lead.

FActive feedback loops

  • Inline keep or remove with a reason, and a rating on each rationale.
  • Weekly prompt and weight updates, published as "you said, we changed".
  • Outcome calibration: predicted vs actual for AI-picked and human-added creators. Used to learn, never to grade people.
  • A monthly AI Council with CDs reviews edge cases and approves weight changes.
  • A golden set of 30-50 past briefs gates every prompt or model change.
The AI earns trust by being checkable, overridable and visibly improving. A Creative Director should feel like the editor, never the reviewer of a machine.
Three layers. Guardrails the AI can't break, because they're code, not prompts. Overrides that are one click and never penalized, so disagreeing with the AI is cheap. Feedback loops that visibly change the product every week, which is what turns skeptics into contributors.

Appendix A5 · Creator Match scoring

A transparent formula, with starting weights to calibrate

match = wperf x Performance + waud x Audience fit + wbrand x Brand fit + wcost x Cost efficiency  (each 0-100)
Components
  • Performance: 70% campaign history vs benchmark, Bayesian-shrunk (k = 3) so one lucky campaign doesn't dominate, plus 30% engagement vs tier median.
  • Audience fit: the share of the creator's audience matching the brief's age, gender and location, from consented demographics or a vendor.
  • Brand fit: Claude's 0-100 judgement from recent captions, tags and comment sentiment, citing posts. If it can't be assessed, audience fit stands in and the row is flagged "not assessed".
  • Cost efficiency: the creator's cost per expected engagement compared with the category benchmark.
Starting weights by objective
ObjectivePerf.Aud.BrandCost

Rules around the score: hard rules first (consent, blocked, competitor work in 90 days, rate cap of 1.2x budget per creator). Then budget fit, at least one rising creator, and flags shown, never dropped. Weights are calibrated with CDs in the pilot, then against campaign outcomes.

If asked why these weights: sales briefs reward proven conversion, awareness rewards reaching the right audience, and community briefs live or die on tone. They are starting points. The pilot calibrates them with CDs, then campaign outcomes calibrate them for real.
Appendix A6 · Likely questions

Short answers to the hard questions

"RMN is our strategy. Why not first?"It's a data product that needs a clean creator graph, commerce attribution, consent and engineers. Phase 1 produces the first three as by-products, so Year 2 starts well ahead instead of from zero.
"How do you get audience data without scraping?"Public metrics via Business Discovery. Demographics via creator OAuth through Creator House, in exchange for insights. A vendor or TikTok One for the rest. Never scraping.
"What if Meta or TikTok change their APIs?"External data lands in BigQuery through one refresh workflow per platform, and scoring reads only from the marts. Pin versions, watch changelogs, keep a vendor fallback.
"Won't it always pick the same big creators?"Tier normalization, Bayesian shrinkage, a rising-creator rule, cost per engagement instead of follower count, and monitoring of how picks spread across tiers.
"How do you know the LLM is any good?"A golden set of 30-50 past briefs: overlap with expert picks, brand-safety recall, rationale faithfulness, JSON validity. It gates every prompt or model change.
"What if the analysts get pulled into reporting?"Campaign Pulse automates part of reporting to buy their time back, and the 70% allocation is my first ask.
"Isn't no-code a bus-factor risk?"Workflows exported to Git, naming conventions, a runbook, analysts cross-trained, and OPS-01 monitoring with alerts.
"What if the CDs refuse?"No mandate. Volunteers first, shadow mode, take away the work they hate, let peers show the results, and respect the off switch.
